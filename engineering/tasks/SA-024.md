# SA-024 — Characterize Clear All transaction scope

Status: DONE
Type: BUG

## Purpose

Determine whether Clear All is atomic across all active lots as required for safe batch reset.

## Current Evidence

`services/run_service.py` currently delegates lot clearing separately before batch cleanup; the audit noted separate transaction boundaries as a potential gap.

## Scope

Inject a failure while clearing one of multiple lots and observe committed End/Current/Event rows.

## Out of Scope

No transaction redesign or database migration.

## Acceptance Criteria

- [AUTO] Failure-injection evidence identifies which rows/events commit or roll back.
- [DB] Observed behavior is compared with ADR-005’s all-lots reset requirement.
- [CODE] If non-atomic behavior is confirmed, create a separate implementation task.

## Verification Required

Use isolated SQLite and an injected store failure; inspect all affected lots after the operation.

## Dependencies

SA-009

## Notes / Constraints

Do not reinterpret Clear All as End Run; `RUN_ENDED` remains forbidden.

## Implementation Summary

Added failure-injection coverage for Clear All transaction scope. The test
confirms that a failure while clearing the second lot leaves the first lot's
End row/event committed while the second lot remains Current. No transaction
behavior was changed.
