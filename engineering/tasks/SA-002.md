# SA-002 — Verify backend health and readiness endpoints

Status: DONE
Type: API

## Purpose

Prove that the independent backend can report liveness and service readiness without a GUI.

## Current Evidence

`api_main.py` starts the backend; `api/recipe_api.py::RecipeApiServer` exposes HTTP routes. `engineering/VERIFICATION.md` records no API-level verification evidence.

## Scope

Test `GET /health` and `GET /api/system/status`, including startup with unavailable PLC/SQL dependencies and observable status fields.

## Out of Scope

No live PLC or SQL Server validation and no GUI changes.

## Acceptance Criteria

- [API] `/health` returns the documented success response while backend dependencies are unavailable.
- [API] `/api/system/status` reports independent SQL and PLC states without crashing the server.
- [AUTO] Tests run with fake/unavailable dependencies.

## Verification Required

Use an isolated backend process or test server and assert HTTP status/body values.

## Dependencies

SA-001

## Notes / Constraints

Do not treat a healthy HTTP response as proof of PLC or SQL connectivity.

## Implementation Summary

Updated the existing stdlib HTTP health route to report backend readiness. The
route now returns HTTP 200 only when a BackendContext and all required service
objects are available to the API. Missing services return HTTP 503 with a
machine-readable missing-service list. PLC and SQL connection state is not
used as the health gate.

Added HTTP-boundary tests for both initialized and missing-service cases,
including a case where PLC and SQL connectivity are false but service objects
are available.
