# SA-011 — Verify Inspection_Current restart recovery

Status: DONE
Type: DB

## Purpose

Prove that backend restart reconstructs active run/lot/disc state from SQLite Current rows.

## Current Evidence

`services/inspection_store.py::recover_current` and `services/run_service.py::recover_state` implement recovery; `api_main.py` invokes recovery during startup.

## Scope

Create active Current rows, restart a controlled backend context, and compare recovered state, identities, counters, and polling eligibility.

## Out of Scope

No GUI migration or live PLC reconnect acceptance.

## Acceptance Criteria

- [DB] Recovery does not create duplicate Start rows or reload data.
- [AUTO] Recovered Run/Lot/Disc identities and scan counts match pre-restart state.
- [API] `/api/operation/state` exposes the recovered authoritative state.

## Verification Required

Use a temporary SQLite database and two backend-context lifecycles, then query state and tables.

## Dependencies

SA-006

## Notes / Constraints

PLC communication availability may be faked; hardware reconnection is covered separately.

## Implementation Summary

Added isolated restart-recovery tests that load two active lots, construct a
new RunService over the same InspectionStore, and verify recovered lot/disc
state, counters, batch activity, and tray data without recreating Start rows.
No production recovery code changed.
