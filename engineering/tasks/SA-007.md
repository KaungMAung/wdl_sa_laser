# SA-007 — Verify changed PLC status/result persistence

Status: DONE
Type: DB

## Purpose

Prove that polling persists only actual status/result changes for affected discs.

## Current Evidence

`services/backend_poller.py::BackendPoller` calls PLC polling; `services/inspection_store.py` updates Current and appends events.

## Scope

Use a fake PLC sequence with unchanged, status-only, result-only, and both-field changes.

## Out of Scope

No real PLC, protocol changes, or full end-run behavior.

## Acceptance Criteria

- [DB] Unchanged values create no update/event.
- [DB] Status changes update only the affected Current row and append `STATUS_CHANGED`.
- [DB] Result changes append `RESULT_CHANGED`; both changes are persisted without rewriting unrelated discs.
- [AUTO] Raw integers and mapped text are retained.

## Verification Required

Run deterministic poll cycles and compare row update timestamps/event counts for affected and unaffected discs.

## Dependencies

SA-001, SA-006

## Notes / Constraints

Identity mismatch behavior is covered separately by PLC task SA-017.

## Implementation Summary

Added deterministic SQLite polling tests covering unchanged polls, status-only
changes, result-only changes, and a later poll where both fields change. The
tests verify that only changed Current fields are updated and matching events
are appended. No production polling or persistence code was changed.

  - Result: 16 tests passed, 0 failures, 0 errors.

  - Result: exit code 0.
- [DB] Unchanged values produced no additional events.
